1. 30초 설명

lfg가 하는 일

Grok(GrokBuild) 안에 OmO 스타일 에이전트 시스템(계획 → 실행 → 리뷰, 규칙, 스킬, 훅)을 설치하고 동기화합니다.

즉 lfg는 “채팅 앱”이 아니라, Grok가 OmO처럼 일하게 만드는 어댑터 + 설치 CLI입니다.

한 문장으로

user
  → lfg setup
  → ~/.grok 에 plugin/agents/hooks/config 기록
  → Grok 세션이 그 설정으로 OmO 루프 실행
중요: npm 패키지 자체는 Grok 플러그인 객체로 보고되지 않습니다 (lfgIsPlugin: false. 대신 setup --run이 실제 플러그인 트리를 ~/.grok/plugins/lfg에 만듭니다.

2. 왜 이 프로젝트가 있나

Upstream (OMO)

OpenCode OmO / lazycodex는 스킬·코어·훅·에이전트 역할이 있는 에이전트 시스템입니다.

원래 홈: OpenCode / Codex 쪽 호스트

Target (GrokBuild)

Grok CLI/호스트는 다른 훅·서브에이전트·설정 표면을 가집니다.

그대로 복붙하면 안 돌아감

lfg의 역할

호스트 중립 코어는 가져오고, Grok 전용 설치/훅/에이전트 연결을 직접 소유합니다.

port + adapter + installer

전략 한 줄: omo-codex는 포장 참고, omo-opencode는 아키텍처 참고, 실제 행동 소스는 공유 *-core + lfg의 Grok glue.

4. 폴더 지도 (코드를 열 때 여기부터)

경로역할언제 보나
bin/lfg.js npm bin 진입점 명령이 안 될 때
src/cli/ CLI 라우팅, JSON 계약, config writer, setup TUI 명령/출력/설정 문제
src/grok/ 설치 엔진, 훅, 에이전트 동기화, MCP 설치 결과/플러그인 문제
src/core/omo/ 호스트 중립 코어 로직 모델/규칙/boulder 동작
skills/ 배포되는 스킬 트리 에이전트 행동 프로토콜
docs/ ADR / 패리티 / 오케스트레이션 문서 설계 의도 확인
dist/ 빌드 산출물 직접 수정 금지

3층 구조만 기억하면 됨

  1. core = 행동 규칙 (호스트 모름)
  2. grok = Grok에 꽂는 어댑터/설치
  3. cli = 사용자 명령과 계약
비유: core는 엔진, grok는 차량 장착 키트, cli는 키와 계기판.

Atlas · 할 일 오케스트레이터

11. Grok-centric multi-model harness — 패리티만으로는 부족한 이유

OMO는 사실상 Claude / GPT / Gemini 행동 전제 위에서 설계·튜닝된 시스템이 많습니다. lfg의 목표는 “파일을 그대로 복사”가 아니라, Grok 4.5를 오케스트레이터로 두고, deep/oracle은 GPT, vision은 Gemini, 나중에는 Z.AI까지 붙이는 Grok 중심 하니스를 만드는 것입니다.

핵심 판정: 현재 OMO parity narrative는 필요하지만 충분치 않습니다. 패리티는 “어떤 컴포넌트/스킬/호스트 표면이 있는가”를 추적합니다. multi-model harness는 “역할별로 어떤 모델이, 어떤 가드레일로, 어떤 프롬프트 변이로 동작해야 하는가”를 추적해야 합니다. 이 둘은 겹치지만 같은 축이 아닙니다.

  • OMO 에이전트 빌더·프롬프트는 Claude/GPT 화법·툴 습관에 맞춰진 구간이 많음
  • Grok는 같은 지시문을 다르게 해석/준수할 수 있음
  • 따라서 init prompt + hook guardrail이 단순 복사로는 약함

호스트/모델 인프라 차이

  • OpenCode system/messages transform 없음 → 턴 단위 가드레일 재주입 약함
  • model-core family detector가 원래 xai/grok를 약하게 다룸 → adapter 보정 필요
  • subagent 모델 오버라이드는 있어도, 역할별 실패 시 cross-family fallback 정책이 약함

D. 패리티 narrative가 여전히 유효한 범위 / 무너지는 범위

계속 유효

  • 스킬 프로토콜 존재 여부 (ulw-plan/start-work/review-work)
  • 호스트 표면 갭 (team, stop reinject, transforms)
  • 코어 이식 여부 (rules/model/prompts/boulder…)
  • “Manifest-only를 Grok-adapted라고 거짓말하지 않기”

이것만으로는 실패

  • Claude식 프롬프트를 Grok orchestrator에 그대로 두고 성공을 기대
  • oracle/deep를 Grok 우선으로 두고 GPT 분업 목표와 충돌
  • vision/Z.AI를 패리티 표의 부록처럼만 취급
  • 설치 시 모델 추천만 하고, 세션 시작 가드레일/역할 계약을 안 심음

E. OMO를 깊게 이해해야 하는 지점 (multi-model 관점)

OMO 영역무엇을 파야 하나Grok에서 달라질 수 있는 구현
agent-builder / prompts-core 역할 프롬프트가 가정하는 모델 습관, tool-calling style Grok orchestrator용 prompt variant + GPT oracle variant 분리
model-core requirements / fallback AGENT_MODEL_REQUIREMENTS, category fallback, capability aliases role→family topology 계약 (orchestrator/deep/vision)
delegate-core spawn 시 모델 선택 로직 Grok lead가 GPT/Gemini worker를 고르는 라우팅 표
hooks (SessionStart/UserPromptSubmit/Stop) 언제 시스템 맥락/가드레일을 주입하는가 Grok 전용 init guardrail bundle (역할 계약, 모델 경계, 금지 행동)
skills (start-work/review-work/ulw-plan) 어떤 역할을 어떤 서브에이전트에 넘기는가 스킬 텍스트의 agent_type/model family 매핑을 Grok topology로 재작성
vision / MCP companions 이미지 도구 경로, provider auth Gemini primary + later Z.AI companion lane

F. lfg에서 OMO와 다르게 구현해야 할 후보

설치 시 (setup)

  • 역할 토폴로지 프리셋: grok-orchestrated
  • agent overrides에 orchestrator/deep/vision family pin
  • init prompt/guardrail 패키지를 plugin assets로 설치
  • unavailable family(GPT/Gemini 없음) 시 명시적 degrade 정책

런타임 시 (hooks/skills)

  • SessionStart: 역할 계약 + 모델 경계 additionalContext
  • UserPromptSubmit: orchestrator self-check (직접 deep work 가로채기 방지 옵션)
  • SubagentStart: worker family/role 검증
  • review/oracle 레인은 GPT 선호 라우팅
아직 확정된 구현이 아님. 위 항목은 “해야 할 연구/설계 후보”입니다. OMO 심층 도씨와 multi-model topology ADR 없이 바로 코딩하면 패리티 표와 실제 제품 목표가 또 어긋납니다.

13. Multimodal requirement — OpenCodex 레퍼런스와 lfg 지원 경로

질문: 멀티모달(이미지 이해/비전 QA)을 어떻게 지원할 것인가? 레퍼런스: 로컬 ~/workspace/ULW/opencodex (src/vision/*, server vision sidecar, provider noVisionModels).

네, 그 레퍼런스를 봤습니다. OpenCodex는 “모든 모델이 native vision을 가진다”고 가정하지 않습니다. 대신 text-only 모델에 눈이 없을 때 vision sidecar로 이미지를 설명 텍스트로 치환하고, 실패하면 main turn을 죽이지 않고 degrade 합니다. lfg의 multimodal 설계도 이 원칙을 가져와야 합니다.

A. OpenCodex가 실제로 하는 일 (reference pattern)

경로

  • src/responses/parser.ts — input_image를 structured image part로 보존 (data URL을 텍스트로 인라인 금지)
  • src/vision/index.ts — planVisionSidecar / describeImagesInPlace
  • src/vision/describe.ts — ChatGPT forward 경로의 GPT vision 모델로 이미지 설명
  • src/server.ts — route 후, no-vision 모델이면 sidecar 실행

규칙

  • Trigger: model ∈ provider.noVisionModels AND request has images
  • Default sidecar model: gpt-5.4-mini (ChatGPT forward/auth 필요)
  • Concurrency 3, per-image desc cap, fail → marker text
  • Sidecar 실패가 main turn abort가 아님 (degrade)
  • Native vision 모델이면 sidecar 없이 image part 그대로 전달
request with image(s)
  → route model
  → if model can see images: pass native image parts
  → else if ChatGPT forward available: vision sidecar describes images → text parts
  → else: degrade marker ("image attached but could not be processed")
  → main model continues

B. lfg / GrokBuild 쪽 현재 상태

Skills visual-qa, artistry/visual-engineering prompts, screenshot/diff workflows Host-level guarantee that Grok lead can “see” every attached image

Z.AI companion lfg zai / lfg-mcp zai-vision package install surface Default multimodal SSOT wired into orchestrator loop

갭: lfg는 “비전 역할/스킬/추천 모델”은 있지만, OpenCodex처럼 요청 경로에서 자동으로 no-vision 모델을 보정하는 harness는 아직 없습니다. 그래서 multimodal requirement를 skill 문서만으로 만족했다고 보면 안 됩니다.

E. 구현 레이어를 어떻게 나눌 것인가

Layer 1 — Capability truth (must)

  • model/provider capability matrix: text / image-in / image-out
  • noVision equivalent list for GrokBuild-discovered models
  • setup/JSON honesty: don’t claim vision if model can’t see

Layer 2 — Role topology (must)

  • vision roles pin to Gemini first
  • oracle/deep stay GPT; orchestrator Grok
  • spawn contracts: visual work → vision specialist, not Sisyphus eyeballing alone

Layer 3 — Sidecar / describe path (should)

  • Borrow OpenCodex semantics: plan → describe → replace/degrade
  • Where it runs: not inside lfg core install by default
  • Candidates: OpenCodex proxy in front of model endpoint, or Grok-side pretool hook/helper, or specialist tool
  • Never inline giant base64 into prompts as fake “vision”

Layer 4 — Protocol skills (must for QA)

  • visual-qa remains protocol SSOT for UI verification
  • evidence = screenshot paths + diff JSON + specialist verdict
  • generation tools (xAI) explicitly separate from understanding

Layer 5 — Companion providers (later)

  • Z.AI vision via lfg-mcp / lfg zai
  • optional, not blocking Gemini primary lane
  • auth isolated from host OIDC

Layer 6 — Guardrails (must)

  • if image present and no vision path: explicit degrade message
  • do not abort whole orchestration turn
  • init/hook guidance: when to spawn vision specialist

F. OpenCodex를 lfg 안으로 “통째 이식”하면 안 되는 이유

가져올 것

  • noVision detection
  • describe-sidecar degrade semantics
  • structured image parts (no data-URL text blowup)
  • sidecar failure isolation

가져오면 안 되는 것

  • Codex-only proxy/inject lifecycle as lfg runtime hard dep
  • ChatGPT forward auth를 Grok host 필수로 만들기
  • vision = generation MCP 라고 섞기
  • OpenCodex 서버를 omo parity 표에 Implemented로 올리기

G. 실제 지원 로드맵 (제안)

14. Multi-provider on GrokBuild — lfg가 지원해야 하는가?

근거: 로컬 Grok 문서 ~/.grok/docs/user-guide/11-custom-models.md, 05-configuration.md, 02-authentication.md. Grok host는 이미 OpenAI-compatible / Anthropic Messages / custom endpoints를 지원한다.

짧은 답: YES — 단, “프로토콜 재구현”이 아니라 “Grok host custom-model surface 위에 올리는 것”. lfg + GrokBuild는 multi-provider를 지원해야 한다. 왜냐하면 우리 harness 목표가 Grok 4.5 orchestrator + GPT deep/oracle + Gemini vision (+ later Z.AI) 이기 때문이다. 그 목표를 Grok-only monorepo로 축소하면 성립하지 않는다.

A. Grok host가 이미 주는 것 (~/.grok/docs)

CapabilityHost surfaceNotes
OpenAI Chat Completions api_backend = "chat_completions" (default) /v1/chat/completions
OpenAI Responses api_backend = "responses" /v1/responses
Anthropic Claude api_backend = "messages" /v1/messages + extra_headers (x-api-key, anthropic-version)
Custom / local OpenAI-compatible [model.*] base_url, Ollama/Together/local servers BYOK or local inference
Model catalog endpoint [endpoints].models_base_url / GROK_MODELS_BASE_URL fetch {base}/models
Auth split per-model api_key/env_key vs host session OIDC host auth.json ≠ provider keys

B. 그래서 lfg가 해야 하는 일 / 하면 안 되는 일

YES — lfg should support

  • setup 시 multi-provider discovery → ~/.grok/config.toml [model.*] 재료화
  • role topology: orchestrator/deep/vision family pin
  • provider-specific base_url / credential slots / context windows
  • Claude 필요 시 api_backend = "messages" + header shape 지원
  • OpenAI-compatible gateway (cliproxy/opencodex/local) 연동
  • unavailable provider degrade 정책
  • keys를 JSON/log에 절대 출력하지 않기

NO — lfg should NOT become

  • OpenCodex/cliproxy 자체를 다시 구현하는 범용 프록시
  • Anthropic/OpenAI SDK를 lfg 코어에 내장한 프로토콜 엔진
  • host auth.json OIDC 소유/변조
  • 모든 provider UX를 lfg CLI 하나로 독점
  • “provider 추가 = OMO parity Implemented” 착각

D. 권장 제품 계약

GrokBuild host
  owns: protocols (chat_completions / responses / messages), TUI model picker, session auth
lfg
  owns: setup materialization, role→model topology, OMO skill harness, guardrails, honesty gates
optional proxies (OpenCodex / cliproxy / corporate gateway)
  own: translation, pools, vision sidecar for text-only models
companions (lfg-mcp / zai)
  own: tool MCP packages, not core inference identity
해석: “Grok가 OpenAI-compatible/Claude를 지원하니 lfg도 지원해야 하냐?” → Yes. 하지만 지원의 의미는 Grok config surface를 올바르게 채우고, multi-model harness를 돌리는 것이지, provider adapter monorepo를 lfg 안에 새로 짓는 것이 아니다.

E. 구현 우선순위 (providers lane)

P1
